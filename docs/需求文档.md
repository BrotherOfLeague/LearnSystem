# Python Docs RAG 知识库需求文档

## 1. 项目概述

### 1.1 项目名称
Python Docs RAG：基于 Python 官方文档的中文智能问答知识库。

### 1.2 项目目标
将 Python 官方文档下载并建立本地可检索的知识库，允许用户使用中文提问，由大语言模型基于检索到的英文官方文档生成中文回答，并提供可核查的来源链接。

本项目采用 RAG（Retrieval-Augmented Generation，检索增强生成）方案，不训练基础大模型。官方文档是答案的主要依据。

### 1.3 核心价值
- 支持中文问题检索英文 Python 官方文档。
- 回答尽可能准确，并提供官方文档出处。
- 保留函数名、参数名、异常名、代码和英文技术术语。
- 采用可替换的检索后端，便于比较 Chroma、PostgreSQL + pgvector 和 Elasticsearch。
- 通过分阶段开发，先完成可运行的最小版本，再优化检索与用户体验。

## 2. 项目范围

### 2.1 第一阶段范围（MVP）
- 以 Python 3.12 官方文档为首个语料版本。
- 下载或导入官方提供的 HTML 文档包。
- 解析 HTML，提取标题、正文、代码块、版本和来源 URL。
- 按文档结构进行文本分块。
- 生成多语言 Embedding 并建立本地向量索引。
- 支持中文问题的语义检索。
- 调用 LLM API，基于检索到的证据生成中文回答。
- 返回答案引用的文档标题、链接及相关原文片段。
- 提供命令行交互方式。
- 编写基础单元测试与端到端测试。

### 2.2 后续迭代范围
- BM25 关键词检索与向量检索融合。
- RRF（Reciprocal Rank Fusion）结果融合。
- 可选 Reranker 重排。
- 检索效果评估集与 Recall@K、MRR 等指标。
- Django + DRF 问答接口。
- Web 聊天界面。
- 多轮对话上下文。
- 文档增量更新、重复检测、索引版本管理。
- 可替换的 Chroma、pgvector、Elasticsearch 检索后端。
- Docker 化部署（按需要实施）。

### 2.3 不在首版范围内
- 训练或微调基础大模型。
- 自动执行用户提交的 Python 代码。
- 自主规划和调用多个工具的 Agent。
- 首版即同时维护三套检索基础设施。
- 企业级多租户、复杂权限、分布式部署和高可用集群。
- 未经许可抓取与分发第三方内容。

## 3. 用户与典型场景

### 3.1 目标用户
希望通过中文学习 Python、查询标准库与语言特性的开发者。

### 3.2 典型场景
1. 用户问：“Python 生成器和迭代器有什么区别？”
2. 用户问：“asyncio.TaskGroup 如何使用？它与 gather 有什么区别？”
3. 用户问：“Python 3.12 中这个功能的行为是什么？”
4. 用户问：“哪个官方文档章节解释了 `__iter__`？”
5. 用户根据上一轮回答继续追问，系统能在有限上下文内保持话题连续。

## 4. 功能需求

### FR-01 官方文档导入
- 支持导入 Python 官方 HTML 文档 ZIP 解压目录。
- 支持记录文档版本、语言、文件路径和官方 URL。
- 导入过程可重复运行，避免无意产生重复文档块。
- 导入失败时记录失败文件与原因，允许重试。

### FR-02 HTML 解析与清洗
- 提取页面标题、正文、段落、列表、代码块和章节层级。
- 尽量去除导航栏、页眉、页脚、侧边栏等非正文内容。
- 保留代码和技术标识符原文。
- 解析结果应可追溯到原始 HTML 文件和 URL。

### FR-03 文本分块
- 优先按照标题、段落、列表和代码块边界切分。
- 支持配置目标块大小、最大块大小和重叠长度。
- 避免把函数签名与紧邻解释拆散。
- 每个 Chunk 保留 source URL、页面标题、章节路径、版本、块序号等元数据。

### FR-04 Embedding
- 首版使用支持中文和英文跨语言语义检索的 Embedding 模型，例如 BGE-M3；具体模型须通过小规模评估确认。
- Embedding 实现必须封装成独立接口，避免业务逻辑绑定单一模型。
- 支持批量生成向量，并对失败请求进行错误记录与重试。
- 若模型本地运行，记录模型名称、版本及向量维度。

### FR-05 向量检索
- 根据用户问题检索相关文档块。
- 支持配置 Top-K 和相似度阈值（阈值应经评估确定，而不是随意固定）。
- 支持基于文档版本、章节或文档类型进行元数据过滤。
- 返回文本、元数据、排名及可用的相似度信息。

### FR-06 混合检索（后续）
- 支持 BM25 关键词检索。
- 支持向量检索与关键词检索的结果融合，首选 RRF。
- 对函数名、参数名、异常名、模块名等技术标识符提供精确匹配能力。
- 混合检索必须可通过配置开关启用，并可单独评估。

### FR-07 重排（后续）
- 可选接入多语言 Reranker，例如 BGE-Reranker-v2-m3，具体选择需通过评估确认。
- 重排只处理初步召回的候选文档，不替代初始检索。
- 应比较重排前后的 Recall、MRR、延迟和资源成本。

### FR-08 LLM 问答
- 调用可配置的大语言模型 API（首选可用的 DeepSeek API，模型名称由配置决定）。
- 提示词要求模型只根据提供的检索证据回答 Python 文档事实问题。
- 证据不足时明确说明不确定或建议查阅官方文档，不得编造出处。
- 中文解释中保留准确的英文术语、代码、函数签名和异常名称。
- 回答应区分官方文档事实与模型补充解释。

### FR-09 引用与可追溯性
- 每条回答尽可能附上来源标题、官方 URL 和支持答案的原文片段。
- 引用链接应来自导入文档的元数据，不由模型自行生成。
- 用户可打开链接核对原始官方内容。
- 无可靠检索证据时，显示“未找到足够的官方文档依据”。

### FR-10 命令行问答
- 支持连续输入问题。
- 提供退出命令。
- 展示答案、引用和检索到的证据摘要。
- 记录必要的运行日志，但默认不记录敏感信息或完整 API 密钥。

### FR-11 API 与 Web（后续）
- 使用 Django + DRF 提供健康检查与问答接口。
- Web 界面支持输入问题、展示回答、查看引用和继续追问。
- API 返回结构化答案、引用列表和错误信息。
- Web UI 与检索后端解耦。

### FR-12 可替换检索后端
- 定义统一 Retriever 接口。
- 至少允许未来实现 Chroma 和 PostgreSQL + pgvector 后端；Elasticsearch 作为全文检索需求明确后的可选后端。
- RAG 编排层不直接依赖具体数据库 SDK。
- 使用同一评估集比较不同后端的检索效果、延迟和维护成本。

### FR-13 评估与测试
- 建立覆盖概念解释、精确术语、标准库、版本差异等类别的问题集。
- 记录每个问题对应的预期文档或证据片段。
- 计算 Recall@5、MRR 等检索指标。
- 对答案进行引用准确性、证据一致性和无依据回答检查。
- 自动化测试覆盖解析、分块、元数据、检索接口和异常路径。

## 5. 非功能需求

### NFR-01 正确性
回答应以检索证据为依据；在证据不足时应承认不确定性。

### NFR-02 可追溯性
每个文档块必须保留可定位到官方页面的元数据。

### NFR-03 可维护性
解析、分块、Embedding、检索、LLM 调用和 API 层职责分离。

### NFR-04 可配置性
模型名称、API 地址、Top-K、分块大小、数据目录等通过配置管理，不硬编码在业务逻辑中。

### NFR-05 安全性
- API Key 存放于环境变量或本地 `.env` 文件。
- `.env`、原始文档和本地索引按项目策略加入 `.gitignore`。
- 不向日志写入密钥。
- 将检索到的文档视为数据，而非可信指令，避免文档内容覆盖系统提示词。

### NFR-06 成本
- 首版优先使用本地文档解析、索引与检索。
- 只有答案生成（以及可选云端 Embedding）产生相应 API 费用。
- 对模型调用设置超时、错误处理和合理的上下文长度限制。

### NFR-07 性能
首版不承诺未经测试的固定吞吐量或延迟。性能目标应在代表性数据集和目标机器上测量后制定。

## 6. 数据与元数据要求

每个文档块建议包含：
- `chunk_id`：稳定唯一标识。
- `document_id`：源文档标识。
- `title`：页面标题。
- `section_path`：章节路径。
- `text`：清洗后的正文文本。
- `source_url`：官方文档 URL。
- `source_path`：本地相对路径。
- `version`：文档版本，例如 `3.12`。
- `language`：文档语言。
- `chunk_index`：块序号。
- `content_hash`：用于去重与增量更新。
- `embedding_model`：生成向量所用模型标识（索引管理信息）。

## 7. 验收标准

### MVP 验收
1. 能导入指定版本的 Python 官方 HTML 文档。
2. 能解析页面标题、正文、代码示例和来源 URL。
3. 能为文档块建立可持久化的向量索引。
4. 用户能用中文提出问题，并得到中文回答。
5. 回答包含可点击的官方来源链接；证据不足时不会伪造引用。
6. 至少通过解析、分块、检索和问答主流程的自动化测试。
7. API 密钥不出现在代码仓库和日志中。
8. 可以重复运行导入流程，且不会无控制地重复写入相同内容。

### 后续版本验收
- 混合检索与纯向量检索可对比。
- 评估报告包含 Recall@5、MRR、引用正确性与响应耗时。
- API / Web 可正常连续问答。
- 至少一个替代 Retriever 实现通过同一接口与评估测试。

## 8. 主要风险与应对

| 风险 | 应对 |
|---|---|
| 中文问题检索英文内容效果不稳定 | 选择多语言 Embedding，增加术语扩展和混合检索，并建立评估集 |
| HTML 页面噪声影响检索 | 使用页面结构解析并人工抽查解析结果 |
| 代码块与解释被错误拆分 | 按章节、段落与代码块边界分块 |
| 模型编造引用 | 引用只从检索结果元数据生成，要求证据不足时拒答或说明限制 |
| 模型或向量维度变更 | 将模型标识和维度纳入索引版本管理，变更时重建索引 |
| 一开始架构过度复杂 | 先实现 MVP，再按评估结果引入 BM25、RRF、Reranker 和 Web |
