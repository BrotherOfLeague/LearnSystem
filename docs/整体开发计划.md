# Python Docs RAG 整体开发计划

## 1. 计划目标

按可验证的阶段构建 Python 官方文档中文问答知识库。每个阶段均有明确产物、任务和验收标准。执行时应一次推进一个 Stage，完成验收后再开始下一阶段。

## 2. 开发原则

1. 先完成端到端最小版本，再优化检索质量。
2. 每个 Stage 都必须产出可运行代码、测试或可检查的文档。
3. 不提前部署不必要的基础设施。
4. 使用固定的问题集评估检索变化，避免仅凭主观感受判断。
5. 所有 Stage 计划文件采用 `Stage-Plan-\d{2}.md` 命名，例如 `Stage-Plan-01.md`。
6. 本文是总体路线图；每个 Stage 的详细执行步骤、文件变更、命令和验收项写在对应 Stage-Plan 文件中。

## 3. Stage 总览

| Stage | 名称 | 核心产出 | 完成标志 |
|---|---|---|---|
| Stage-01 | 项目初始化与环境配置 | Poetry 项目、目录、配置与测试框架 | 环境可安装、测试可运行 |
| Stage-02 | 官方文档获取与解析 | HTML 文档导入、解析器、导入报告 | 能提取正文、代码、标题和 URL |
| Stage-03 | 文本分块与元数据 | Chunker、分块产物、数据校验 | 分块完整且来源可追溯 |
| Stage-04 | Embedding 与 Chroma 索引 | Embedding 接口、向量入库、持久化索引 | 文档可向量检索 |
| Stage-05 | 基础 RAG 中文问答 | Retriever、Prompt、LLM Client、CLI | 中文问题可得到有出处的回答 |
| Stage-06 | 评估集与检索质量基线 | 30–50 个问题、Recall@5、MRR 等报告 | 能重复评估检索效果 |
| Stage-07 | BM25 + RRF 混合检索 | 关键词检索、融合算法、对比报告 | 精确术语与语义查询均可测试 |
| Stage-08 | 查询改写与可选重排 | Query Processor、Reranker 适配器 | 评估证明有收益，或明确记录不采用 |
| Stage-09 | FastAPI 服务化 | 问答 API、健康检查、接口测试 | 可通过 HTTP 问答 |
| Stage-10 | Web 聊天界面 | 输入框、回答、引用、连续追问 | 可通过浏览器使用 |

| Stage-12 | 后端对比与部署整理 | pgvector / Elasticsearch 评估、README、部署说明 | 基于指标决定是否迁移或增加后端 |

## 4. 每个 Stage 的执行约定

每个 `Stage-Plan-XX.md` 必须包含：
- 目标与范围。
- 前置条件。
- 具体任务，按顺序编号。
- 涉及或新增的文件路径。
- 运行命令。
- 自动化测试。
- 验收标准。
- 常见失败及排查方式。
- 完成记录与后续 Stage 的输入。

除非当前 Stage 验收通过，否则不应跳到后续 Stage。若发现前置设计有问题，先更新设计文档并说明影响。

## 5. Stage 详细路线

### Stage-01：项目初始化与环境配置
- 建立 Poetry 项目。
- 配置 Python 3.12、基础依赖与 pytest。
- 建立 `src`、`tests`、`data`、`storage` 目录。
- 建立 `.env.example` 与 `.gitignore`。
- 增加最小配置读取和启动检查。

验收：新环境可按 README 安装依赖，测试命令成功。

### Stage-02：官方文档获取与解析
- 下载指定版本 Python 官方 HTML 文档。
- 建立 Loader 和 HTML Parser。
- 提取页面标题、正文、代码块、章节路径和 URL。
- 输出解析统计与失败清单。
- 准备少量固定 HTML 测试样例。

验收：能从代表性页面提取可读正文，代码与 URL 不丢失。

### Stage-03：文本分块与元数据
- 定义 Document 和 Chunk 数据模型。
- 实现按标题、段落、列表和代码块的结构化切分。
- 生成稳定 chunk ID 和 content hash。
- 保存 JSONL 等便于调试的分块产物。
- 检查空块、过长块、重复块和缺失 URL。

验收：每个 Chunk 都可追溯到官方页面，关键代码块保持完整。

### Stage-04：Embedding 与 Chroma 索引
- 定义 EmbeddingProvider 与 VectorStore 接口。
- 接入候选多语言 Embedding 模型。
- 在小样本上验证中文问题对英文文档的检索能力。
- 实现批量向量生成、Chroma upsert 与持久化。
- 记录模型名称、版本和向量维度。

验收：重启程序后索引仍存在；查询可返回原文与元数据。

### Stage-05：基础 RAG 中文问答
- 实现 Retriever。
- 实现可配置的 LLM Client。
- 构建包含证据编号、原文和 URL 的提示词。
- 实现 CitationBuilder 和证据不足处理。
- 实现 CLI 连续问答。

验收：中文问题得到中文回答，并且引用链接来自真实检索结果。

### Stage-06：评估集与基线
- 建立 30–50 个带预期文档的中文问题。
- 覆盖概念、API、代码示例、版本差异和边界问题。
- 实现 Recall@5、MRR、引用准确性检查。
- 记录基线结果、耗时和错误案例。

验收：任何检索优化都可以和固定基线比较。

### Stage-07：BM25 + RRF
- 为文档块建立关键词索引。
- 对 API 名、函数名、异常名等术语进行检索测试。
- 实现 RRF 结果融合与去重。
- 对比向量检索与混合检索的评估结果。

验收：输出对比报告，并明确混合检索是否提升目标指标。

### Stage-08：查询改写与可选重排
- 先分析 Stage-06 / Stage-07 的失败案例。
- 对中文问题生成辅助英文查询或技术关键词。
- 需要时接入多语言 Reranker。
- 比较改写、重排前后的质量与延迟。
- 若收益不明显，不启用额外组件。

验收：每项新增能力均有量化对比或明确的不采用理由。

### Stage-09：FastAPI 服务化
- 将 RAGService 与 CLI 解耦。
- 增加 `/health` 与问答端点。
- 定义 Pydantic 请求和响应模型。
- 处理参数校验、超时和异常。
- 增加 API 集成测试。

验收：客户端可通过 HTTP 发送问题并接收回答与引用。

### Stage-10：Web 聊天界面
- 选择轻量前端实现方式。
- 支持输入问题、加载状态、错误提示。
- 展示 Markdown 答案、代码块和来源链接。
- 支持连续追问，并明确会话上下文范围。

验收：浏览器端可以完成完整问答流程。

### Stage-11：文档更新与索引管理
- 基于 content hash 检测变更。
- 支持重复导入、变更更新与失效块删除。
- 管理 Python 文档版本。
- 提供索引重建与状态查看命令。

验收：重复导入不会无控制地增加重复块，版本元数据清晰。

### Stage-12：后端对比与部署整理
- 保持统一 Retriever 接口。
- 在需求确实需要时实现 pgvector 或 Elasticsearch 适配器。
- 用同一评估集测试召回、排名、延迟和运维复杂度。
- 补充 README、配置说明、备份与恢复说明。
- 根据实际使用方式决定是否 Docker 化。

验收：有可复现的技术选型依据；不要求必须同时部署全部后端。

## 7. 版本里程碑

### Milestone A：本地可用
完成 Stage-01 至 Stage-05。
结果：可以在命令行使用中文向 Python 官方文档提问。

### Milestone B：检索质量可验证
完成 Stage-06 至 Stage-08。
结果：可以量化比较纯向量检索、混合检索和重排。

### Milestone C：可交互应用
完成 Stage-09 至 Stage-10。
结果：通过 HTTP API 和网页界面使用知识库。

### Milestone D：可维护与可扩展
完成 Stage-11 至 Stage-12。
结果：支持版本更新、索引管理，并能根据评估结果选择数据库后端。

## 8. 首个执行任务

从 `Stage-Plan-01.md` 开始。先完成项目初始化、依赖管理、配置读取和测试框架，不要同时开发解析器、Embedding 或 RAG。

完成 Stage-01 后，检查环境与测试全部通过，再进入 Stage-02。
