# 核心原理

> 本文档集中解释 LearnSystem 用到的重要技术原理，每个主题独立成节，便于理解「为什么会这样设计」。

## 1. RAG（检索增强生成）

RAG = **R**etrieval **A**ugmented **G**eneration。

核心思想：把问答拆成两段——

1. **检索（Retrieval）**：从本地文档库里捞出与问题相关的"证据"片段；
2. **生成（Generation）**：把证据喂给 LLM，让它"照着资料答题"。

```
用户问题 ──► 检索 ──► Top-K 证据 ──► 拼进 Prompt ──► LLM ──► 回答 + 引用
```

**为什么需要 RAG**：LLM 的训练数据里没有本地文档（如 Python 3.15 官方文档），直接问会凭印象回答甚至编造。RAG 把文档原文作为证据注入，回答有据可依、可追溯。

**本项目落地**（`RAGEngine.ask()` 五步）：

```
① 检索   Retriever.retrieve()     问题→向量化→向量检索 Top-K
② 过滤   score >= 0.3 的保留
③ 组装   _build_context()          [1](来源 URL) 原文…… [2](来源 URL)……
④ Prompt _build_prompt()           回答规则 + 对话历史 + 证据 + 问题
⑤ 生成   LLMClient.generate()     回答；_extract_sources() 取引用链接
```

## 2. Embedding（文本向量化）

Embedding 是把**文字变成数字向量**的过程，让计算机能"算"文字之间的语义相似度。

```
"如何读取 JSON 文件？"  ──►  [0.12, -0.83, 0.45, ..., 0.67]   (1024 维)
"How to read a JSON file?" ──►  [0.15, -0.80, 0.43, ..., 0.65]  (相近)
```

- 语义相近的句子 → 向量距离近；语义无关 → 距离远。
- 本项目的文档块和问题都被编码成 **1024 维**向量，用余弦相似度比较。

---

## 3. BGE-M3 模型

BGE-M3 是智源研究院（BAAI）开源的多语言文本向量模型。

**M3 = 三个 Multi**：

| 维度 | 含义 |
|---|---|
| Multi-linguality 多语言 | 支持 100+ 语言（中、英、日…） |
| Multi-functionality 多功能 | 稠密 / 稀疏 / 多向量三种检索模式 |
| Multi-granularity 多粒度 | 长文↔短文都能匹配 |

关键参数：底座 XLM-RoBERTa、约 5.7 亿参数、稠密输出 1024 维。

本项目只用它的**稠密（dense）模式**做跨语言检索，模型配置在 `.env` 的 `EMBEDDING_MODEL`（指向本地下载的模型目录）。

---

## 4. 中英文跨语言 Embedding 对齐原理

**为什么中文问题能搜到英文文档**：因为 bge-m3 把中英文映射到了**同一个向量空间**。

三层机制：

1. **多语言底座**：XLM-RoBERTa 在 100 种语言上预训练，中英文共用同一 tokenizer 和词表。
2. **对比学习 + 平行语料**：用「中英同义句对」做正样本拉近、"无关句对"做负样本拉远，让模型学会"语义相同 ⇒ 向量相近"。
3. **同一模型编码**：文档（英文）和问题（中文）都用同一个 bge-m3，不经过翻译，直接在同一个空间比较。

```
        向量空间（1024 维）
  "sorted 函数怎么用"(中) ●  ← 距离近
  "How to use sorted"(英) ●
  "什么是生成器"(中)      ○  ← 距离远
```

> 注意："一样"是**语义相近**，不是完全相同。某些中文概念→英文术语的映射仍有偏差（如"装饰器"检索偏弱），这是跨语言模型的固有局限。

## 5. 向量检索与相似度

检索时，把问题向量和所有文档块向量逐一比较相似度，取最相近的 Top-K。

**余弦相似度**（本项目使用，Chroma 配置 `hnsw:space=cosine`）：

```
similarity = cos(θ) = (A·B) / (|A|·|B|)
```

- 值域 [-1, 1]，越接近 1 越相似；本项目检索时把距离转成相似度（`score = 1 - distance`）。
- `RAGEngine` 用 `min_relevance_score=0.3` 过滤低相关的块。

---

## 6. 文本分块（Chunking）

文档太长，直接编码会稀释语义，所以要切成小块。

本项目的 `RuleBasedChunker`：

- 按**段落边界 + 代码块边界**切分（代码块不被截断）；
- 目标 ~800 字符、重叠 120 字符；
- 每块保留 `source_url`、`section_path` 等元数据，用于溯源。

最终 581 篇文档 → **18,943 个分块**，每块都能追溯到官方页面 URL。

---

## 7. LLM 生成与引用溯源

最后一步：把检索到的证据拼进 Prompt，让 LLM 生成回答。

三个关键机制：

1. **证据编号**：证据以 `[1]`、`[2]` 编号注入 Prompt，LLM 回答时用编号标注。
2. **引用可追溯**：回答底部的来源链接由程序从检索结果的元数据生成，LLM 无法伪造。
3. **证据不足不编造**：没有相关证据时，直接回答"无法根据资料回答"。
