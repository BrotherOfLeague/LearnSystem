# 核心原理

> 本文档集中解释 LearnSystem 用到的重要技术原理，每个主题独立成节，便于理解「为什么会这样设计」。

## 1. RAG（检索增强生成）

RAG = **R**etrieval **A**ugmented **G**eneration。

核心思想：把问答拆成两段——

1. **检索（Retrieval）**：从本地文档库里捞出与问题相关的"证据"片段；
2. **生成（Generation）**：把证据喂给 LLM，让它"照着资料答题"。

```
用户问题 ──► 检索 ──► Top-K 证据 ──► 拼进 Prompt ──► LLM ──► 回答 + 引用
```

**为什么需要 RAG**：LLM 的训练数据里没有本地文档（如 Python 3.15 官方文档），直接问会凭印象回答甚至编造。RAG 把文档原文作为证据注入，回答有据可依、可追溯。

**本项目落地**（`RAGEngine.ask()` 五步）：

```
① 检索   Retriever.retrieve()     问题→向量化→向量检索 Top-K
② 过滤   score >= 0.3 的保留
③ 组装   _build_context()          [1](来源 URL) 原文…… [2](来源 URL)……
④ Prompt _build_prompt()           回答规则 + 对话历史 + 证据 + 问题
⑤ 生成   LLMClient.generate()     回答；_extract_sources() 取引用链接
```

## 2. Embedding（文本向量化）

Embedding 是把**文字变成数字向量**的过程，让计算机能"算"文字之间的语义相似度。

```
"如何读取 JSON 文件？"  ──►  [0.12, -0.83, 0.45, ..., 0.67]   (1024 维)
"How to read a JSON file?" ──►  [0.15, -0.80, 0.43, ..., 0.65]  (相近)
```

- 语义相近的句子 → 向量距离近；语义无关 → 距离远。
- 本项目的文档块和问题都被编码成 **1024 维**向量，用余弦相似度比较。

---

## 3. BGE-M3 模型

BGE-M3 是智源研究院（BAAI）开源的多语言文本向量模型。

**M3 = 三个 Multi**：

| 维度 | 含义 |
|---|---|
| Multi-linguality 多语言 | 支持 100+ 语言（中、英、日…） |
| Multi-functionality 多功能 | 稠密 / 稀疏 / 多向量三种检索模式 |
| Multi-granularity 多粒度 | 长文↔短文都能匹配 |

关键参数：底座 XLM-RoBERTa、约 5.7 亿参数、稠密输出 1024 维。

本项目只用它的**稠密（dense）模式**做跨语言检索，模型配置在 `.env` 的 `EMBEDDING_MODEL`（指向本地下载的模型目录）。

---

## 4. 中英文跨语言 Embedding 对齐原理

**为什么中文问题能搜到英文文档**：因为 bge-m3 把中英文映射到了**同一个向量空间**。

三层机制：

1. **多语言底座**：XLM-RoBERTa 在 100 种语言上预训练，中英文共用同一 tokenizer 和词表。
2. **对比学习 + 平行语料**：用「中英同义句对」做正样本拉近、"无关句对"做负样本拉远，让模型学会"语义相同 ⇒ 向量相近"。
3. **同一模型编码**：文档（英文）和问题（中文）都用同一个 bge-m3，不经过翻译，直接在同一个空间比较。

```
        向量空间（1024 维）
  "sorted 函数怎么用"(中) ●  ← 距离近
  "How to use sorted"(英) ●
  "什么是生成器"(中)      ○  ← 距离远
```

> 注意："一样"是**语义相近**，不是完全相同。某些中文概念→英文术语的映射仍有偏差（如"装饰器"检索偏弱），这是跨语言模型的固有局限。

## 5. 向量检索与相似度

**匹配的本质是「向量相似度」，不是「关键词匹配」。** 分三步：

```
① 编码   问题 → bge-m3 → 1024 维向量
② 相似度 问题向量 与 18,943 个文档块向量 逐个算余弦相似度
③ 排序   相似度从高到低排，取 Top-K
```

**余弦相似度**（Chroma 配置 `hnsw:space=cosine`）：

```
similarity = cos(θ) = (A·B) / (|A|·|B|)
```

- 值域 [-1, 1]，越接近 1 越相似；代码里把距离转成相似度（`score = 1 - distance`）。
- `RAGEngine` 用 `min_relevance_score=0.3` 过滤低相关的块。

**具体例子**（问「有哪些内置函数」）：

```
问题 "有哪些内置函数" → bge-m3 → 问题向量
   │ 和 18,943 个文档块向量算余弦相似度
   ▼
命中 Top-8（按相似度排序）：
  [1] builtins/functions.html   ← "Built-in functions"（0.72）
  [2] whatsnew/3.0.html
  ...
```

**为什么是语义匹配**：问题是中文"内置函数"，文档是英文"Built-in functions"，词面完全不同，但 bge-m3 把它们编码到相近位置，所以能匹配上。

**怎么做到"快"：HNSW 近似最近邻**

当前 18,943 个向量、每个 1024 维，暴力算余弦约 1900 万次乘加，几十毫秒也能扛，但百万级就慢。所以向量库统一用 **HNSW**（Hierarchical Navigable Small World，分层可导航小世界），复杂度从 O(N) 降到约 O(log N)。

HNSW 把向量组织成**多层图**，搜索时"高处大步跳、低处精找"：

```
        稀疏的顶层（大步跳）
        ●───●─────●
       /     │
      ●──●───●───●────●     中层
     /    \  │   │
    ●─●─●──●─●───●─●─●─●    稠密的底层（精找）
```

- **顶层稀疏**：节点少、连得远，负责大方向；
- **底层稠密**：节点全、连得近，负责精确。

搜索过程（类似跳表）：从顶层入口贪婪地跳到"离目标更近"的邻居 → 逐层往下、步幅变小 → 到底层局部精搜。类比"先看全国地图定位到省，再看市、再看街道"。

**"近似"的含义**：HNSW 是近似最近邻，不保证 100% 找到绝对最近，但通常能找回 95%+ 的真实最近邻，换来毫秒级速度和百万级扩展能力。精度与速度可用 `M`、`ef_search` 等参数权衡——对 RAG 场景，近似足够。

**落地**：Chroma 建 collection 时配置 `hnsw:space=cosine`，建索引时构建 HNSW 图，检索时 `collection.query(...)` 走 HNSW 分层跳转，毫秒级返回 Top-K。

## 6. 文本分块（Chunking）

文档太长，直接编码会稀释语义，所以要切成小块。**581 篇文档 → 18,943 个分块**（平均每篇约 33 块，每块约 779 字符）。

**分块器 `RuleBasedChunker` 的参数**（`rule_based_chunker.py` + `.env`）：

| 参数 | 值 | 含义 |
|---|---|---|
| `target_size` | 800 | 目标块大小（字符） |
| `max_size` | 1200 | 单块上限 |
| `overlap` | 120 | 相邻块重叠 |
| `min_size` | 100 | 过小的尾巴块合并 |

**分块流程**：

```
一篇文档正文
   │
   ▼
① 按空行切成「段落」
   ▼
② 段落里识别「代码块」（```...```）
   ├── 代码块 → 单独成块，绝不截断
   └── 普通段落 → 累积到接近 1200 字符才截断
   ▼
③ 超长段落按词再切（带 120 字符重叠）
   ▼
④ < 100 字符的小尾巴合并进前一块
   ▼
每块 = 文本 + 溯源元数据
```

**具体例子**：`library/json.html`（约 2.5 万字符）→ 约 45 块，其中代码块完整保留换行缩进。

**每个块的元数据**：

```python
Chunk(
    chunk_id     = "doc_xxx_chunk_0031",          # 唯一 ID
    document_id  = "doc_xxx",                      # 所属文档
    chunk_index  = 31,                             # 文档内序号
    text         = ">>> import json ...",          # 块正文
    code_blocks  = [">>> import json ..."],        # 代码块单独存
    section_path = ["...", "json — ..."],          # 章节路径
    source_url   = "https://.../library/json.html",# 溯源
    version      = "3.15",
    content_hash = "md5...",                       # 去重用
    char_count   = 428,
    token_estimate = 107,
)
```

**为什么块数不固定**：18,943 是"自然切分"的结果，不是预设数字——短页面 1 块、长页面几千块，由「文档长度 ÷ 约 800 字符」决定。

**质量保证**：

1. 代码块不截断（超过 1200 字符也整块保留）；
2. 优先在段落边界断，不跨段落乱切；
3. 超长段落按词切时保留 120 字符重叠，避免语义断裂；
4. 每块带 `source_url` / `section_path`，命中后可反查官方页面。

这些块就是向量化的输入：18,943 块 → bge-m3 → 18,943 个 1024 维向量 → 存进 Chroma。

## 7. LLM 生成与引用溯源

最后一步：把检索到的证据拼进 Prompt，让 LLM 生成回答。

三个关键机制：

1. **证据编号**：证据以 `[1]`、`[2]` 编号注入 Prompt，LLM 回答时用编号标注。
2. **引用可追溯**：回答底部的来源链接由程序从检索结果的元数据生成，LLM 无法伪造。
3. **证据不足不编造**：没有相关证据时，直接回答"无法根据资料回答"。

## 8. 为什么有时需要全量重建索引（增量 vs 全量）

**核心原则：数据变了 → 增量处理；处理逻辑/模型变了 → 全量重建。**

### 增量 vs 全量

| 场景 | 处理方式 | 原因 |
|---|---|---|
| 新增/删除文档 | 增量 | 用 `source_hash`（原始文件 MD5）检测，只处理变化的 |
| 修改文档内容 | 增量 | 同上，只重新解析变化的文件 |
| **改解析器/分块器** | **全量重建** | 处理逻辑变了，所有文档的解析/分块结果都变 |
| **换 embedding 模型** | **全量重建** | 向量空间变了，旧向量不能和新向量共存 |

### 为什么改解析器要全量重建

文档向量是「解析 → 分块 → embedding」这条管线生成的，每一环都影响最终向量：

```
原始文件 ──解析──► 正文 ──分块──► chunk ──embedding──► 向量 ──入库──► Chroma
              ↑改动          ↑正文变了       ↑chunk_id 变了    ↑旧向量过时
```

- 改了解析器（比如加"函数清单摘要"）→ 正文文本变了 → content_hash 变 → document_id 变 → chunk_id 变；
- 旧索引里的向量块是"旧文本"生成的，和新解析结果对不上；
- 必须清空索引，全部重新解析 + 重新向量化。

### 为什么换 embedding 模型必须全量重建

向量库里的所有向量必须来自**同一个模型、同一个语义空间**：

- 换了 embedding 模型，新向量的维度或语义空间可能不同；
- 新旧向量混在同一个库里，余弦相似度就失效了（苹果和橘子不能比）；
- 所以换模型必须清空重建。

### 本项目的落地命令

```bash
# 增量导入（数据变化时用，未变文档复用）
poetry run python -m learn_system.loaders.import_docs

# 全量重新解析（改了解析器/分块器后用）
poetry run python -m learn_system.loaders.import_docs --full

# 追加导入另一个文档来源（多来源合并，保留已有来源）
poetry run python -m learn_system.loaders.import_docs --docs-dir ./data/raw/sklearn-1.9-docs --base-url https://scikit-learn.org/stable --version 1.9 --append

# 增量建索引（只处理新增块 + 清理删除的）
poetry run python -m learn_system.cli.build_index

# 全量重建索引（改解析器/分块器/embedding 模型后用）
poetry run python -m learn_system.cli.build_index --rebuild
```

**一句话**：判断"数据变了"用增量，判断"处理逻辑或模型变了"必须全量重建。
